# Изоляция исполнителей

Навык управляется agent-kit {{KIT_VERSION}}. Не запускай параллельно несколько
субагентов, изменяющих существующие файлы в одном workspace: записи могут
перезаписать друг друга даже при логически разных задачах.

## Выбор режима

- Read-only задачи можно запускать параллельно в пределах concurrency.
- Параллельный create-only без worktree допустим только с явными
  непересекающимися списками новых путей. Проверь, что пути не существуют;
  запрети любые изменения существующих файлов. Общие точки регистрации
  (`.sln`, `.csproj`, манифесты, индексы) меняет главный агент последовательно.
- Один write-субагент без других параллельных write-делегаций может работать
  в основном workspace. Главный агент не должен одновременно менять его файлы.
- Для нескольких параллельных write-задач создай отдельный git worktree
  каждому исполнителю. Выдай точный рабочий каталог и запрети запись вне него.
  Передай контракты, критерии приёмки, проектные правила и команды проверок.

## Команды

В Windows используй `.\scripts\agent-worktree.cmd` с теми же аргументами.

```bash
scripts/agent-worktree create <task-name>
scripts/agent-worktree list
scripts/agent-worktree diff <task-name>
scripts/agent-worktree merge <task-name>
scripts/agent-worktree remove <task-name>
```

`create` готовит `.worktrees/<task-name>` на ветке `agent/<task-name>`;
`diff` показывает изменения относительно базы; `merge` выполняет `--no-ff`;
`remove` удаляет worktree и ветку. Перед применением проверь справку скрипта
и состояние Git. `.worktrees/` исключён из Git.

## Подготовка инструментов перед write-делегацией

1. Различай три пути: рабочий каталог исполнителя (в выданном worktree),
   корень проекта-потребителя (сам worktree или нужный проект внутри него)
   и расположение установленного CLI. Основной checkout — возможное место
   установки CLI, но не корень проекта для работы в делегированном worktree.
2. Определи необходимые инструменты по правилам и манифестам проекта.
   Отсутствие `node_modules` в worktree, команды в `PATH` или результатов
   glob-поиска не доказывает, что CLI отсутствует: glob может пропустить
   игнорируемые файлы. Проверь точные пути (например, `test -f` или
   `Test-Path -LiteralPath`) в известных местах установки, включая основной
   checkout, и требуемую среду запуска.
3. Соблюдай порядок выбора по контракту инструмента. Если путь не задан явно
   пользователем или хостом, предпочитай установку проекта в worktree или его
   объявленном workspace. Если её нет, главный агент может выбрать уже
   установленный CLI основного checkout по абсолютному пути, если контракт
   допускает отдельную установку. Для focused-spec следуй штатному загрузчику, включая
   возможность выбрать установленный CLI из `PATH`. Не меняй явно выбранный
   исполняемый файл молча.
4. До делегации проверь запуск выбранного CLI безопасной командой из выданного
   worktree, в той же среде и оболочке, что и у исполнителя. Для focused-spec
   получай `instructions` отдельным вызовом без `--root`, с темой по задаче.
   Используй версию из проверенного ответа `instructions`, не добавляй вызов
   `version` для того же шага. Сверь версию CLI с точной версией в lock-файле
   worktree, если она закреплена, и с ограничением манифеста, если оно задано.
   Не принимай тег `latest` за точную версию. Не используй несовместимый CLI;
   при блокере укажи требуемую и найденную версии и путь к CLI.
   В Windows проверяй `.cmd`-обёртку (в PowerShell: `& "<путь к CLI.cmd>"`)
   или объявленную точку входа пакета через подходящий runtime. Заключай пути
   с пробелами в кавычки, используй пути и runtime своей среды (Windows или
   WSL) и не меняй `ExecutionPolicy`.
5. Только после проверки передай исполнителю рабочий каталог, корень проекта,
   точные пути к CLI и, если нужно, к среде запуска, а также проверенные команды
   с аргументами для его оболочки. Тем же CLI focused-spec выполняй команды,
   читающие проект (например, `list --root "<корень проекта>"`), передавая
   `--root` на корень проекта внутри worktree по контракту CLI.
6. Тесты, сборку и проектные плагины запускай с зависимостями проекта в
   выданном worktree или его объявленном workspace. Проверь, откуда они
   разрешаются: для вложенного worktree поиск по родительским каталогам может
   найти `node_modules` основного checkout даже при верном корне проекта.
   Не используй такую подмену и не создавай общую ссылку на `node_modules`.
7. Если нужный инструмент недоступен, сообщи проверенные пути, каталог запуска
   и конкретную причину: файл отсутствует или команда завершилась ошибкой
   (укажи команду и диагностику). Не скачивай пакеты самовольно, в том числе
   через `npx` или `npm exec`, и не обходи требования focused-spec.

## Приёмка и слияние

- Проверяй не только статус делегации, но и содержательность результата,
  diff, контракты и фактически выполненные проверки.
- Пустой ответ, ошибка, обрыв или отсутствие запрошенного итога — не успех.
  Перезапусти задачу с требованием вернуть итог и диагностику; при повторной
  неудаче выполни сам и сообщи об ограничении. При лимите concurrency повторяй
  незавершённые задачи последовательно.
- Merge выполняет только главный агент, последовательно, по одному worktree,
  при чистом основном дереве. Изменения должны быть закоммичены в ветке;
  коммиты и merge делай только при разрешении пользователя на эти действия.
- После merge выполни сборку и тесты затронутых систем. При конфликте остановись
  и разреши его с приоритетом контрактов и `project-memory/`; не затирай
  пользовательские изменения. Не обходи проверку чистоты основного дерева.
- После успешной интеграции удали worktree штатной командой `remove` только
  когда нет несохранённых результатов и разрешено удаление ветки.
