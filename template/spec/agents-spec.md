## OmO and focused-spec Executable Specifications

`focused-spec` {{FOCUSED_SPEC_VERSION}} дополняет обычное планирование и
исполнение OmO и не заменяет `ulw-plan`, планы `.omo/plans/`, сборки,
регрессионные проверки и QA. Правила раздела действуют, только когда
пользователь явно просит создать или изменить спецификацию либо спланировать
или реализовать задачу по названной утвержденной спецификации. Наличие
`.focused-spec/config.yaml` или постороннего `spec.md` не делает задачу
SDD-задачей; простые задачи идут обычным порядком без новой спецификации.

Ниже — правила размещения и приемки проекта. Синтаксис inline-сценариев,
протокол evidence и порядок работы берет установленный навык `focused-spec`
через локальный CLI; эти правила не заменяют его workflow.

- **Спецификация возможности** `specs/<capability>/spec.md` описывает
  действующее поведение. ID устойчив в пределах scope и не меняется при
  переносе принятого сценария; проект использует префикс возможности.
- **Спецификация изменения** `specs/changes/<change>/spec.md` содержит
  сценарии одного изменения. Если есть CHG, scope называется по нему
  (`chg-0042-<slug>`); имена scope двух слоев не должны совпадать.
  Каждый сценарий, включая изменение действующего поведения, самостоятельно
  указывает свой ID и точное evidence; повторение ID в другом scope не
  связывает сценарии и не наследует evidence.
  До приемки действующую спецификацию владельца не правят.
- **Закрытие изменения** после успешного запуска всех его сценариев:
  перенести принятое поведение и evidence в спецификацию возможности,
  заменить прежний сценарий с тем же ID либо удалить снятое поведение,
  затем переместить изменение в `specs/archive/<change>/` (вне discovery).
  Запустить локальный `focused-spec run --scope <capability>` для каждого
  затронутого владельца; результаты зафиксировать в плане или CHG.
  Архив — история: его не правят и не возрождают.
- Небольшое изменение одной возможности допускается прямо в спецификации
  владельца без спецификации изменения; приемкой служит полный `run` владельца.

Роли:

- **Требования (Sisyphus).** Загрузи официальный навык `focused-spec` из
  `.opencode/skills/focused-spec/SKILL.md` и его актуальный workflow из
  проектного CLI. По явному запросу пользователя размещай сценарии по слоям
  выше; сохраняй точное evidence каждого сценария. Еще не написанные тесты
  помечай `planned:`. Перед передачей выполни локальный
  `focused-spec validate --scope <scope>` без `--strict`: это проверка
  планирования, а не доказательство реализации. Утверждение требований само
  по себе не разрешает планирование или написание кода.
- **План (Prometheus).** Прочитай названную спецификацию и текущий код.
  Спецификация остается источником согласованных требований, план задает
  порядок исполнения. Укажи в плане путь и scope спецификации, сопоставь
  каждый ID сценария задачам плана и сделай обязательными шагами приемки
  создание тестов, замену `planned:`, локальный `focused-spec run --scope <scope>`
  и, для спецификации изменения, ее закрытие в спецификации владельцев.
  Добавь миграции, документацию, CHG/ADR, интеграционные проверки и реальное
  QA, если они нужны. Не переписывай требования в отдельную спецификацию;
  о противоречиях и нужных поправках сообщай пользователю, не правь
  спецификацию вне разрешенных планировщику путей и не обходи это
  делегированием. Не реализуй.
- **Исполнение (Atlas/Sisyphus).** Передавай каждому исполнителю путь
  спецификации, scope и ID сценариев его задачи. Пиши настоящие тесты,
  проверяющие каждый `THEN`, затем реализуй поведение и замени `planned:`
  точными селекторами. Перед завершением выполни локальный
  `focused-spec run --scope <scope>` для всего принятого scope на текущем коде.
  `run` сам выполняет строгую валидацию; один `validate`, нулевой код без
  выполненных тестов, SKIP/ERROR или оставшийся `planned:` не считаются
  успехом. Не используй `--allow-skip`, чтобы обойти отсутствующую БД или
  другую обязательную проверку. Сценарии с БД выполняй только на одноразовых
  БД по правилам проекта. Для спецификации изменения затем закрой изменение.
- **Приемка.** Запиши команды, результаты и проверенную ревизию кода в
  evidence плана или отчет; любое изменение кода после проверки требует
  повторить затронутые проверки. Для рискованных задач добавь независимую
  проверку в свежем контексте по цепочке «требование → утверждения тестов →
  реализация»; замечания возвращаются исполнителю. Пройденные тесты
  доказывают только то, что они реально проверяют, а не полноту требований.

Baseline `project-memory/` сохраняет приоритет: спецификация не переопределяет
ADR и согласованные требования молча, изменения идут через CHG/ADR. До первой
спецификации discovery не находит документов — это ожидаемо и не является
успешной проверкой.

При чистой установке языковые runner'ы не подключены (`runners: {}`). При
первой задаче, требующей тестов, сам подготовь окружение под стек проекта:

1. Прочитай инструкции проекта, манифесты, lock-файлы, настройки CI и текущие
   команды тестов. Используй существующий тестовый фреймворк; не добавляй
   Python или .NET только ради focused-spec.
2. Проверь доступные инструменты и зависимости. Установи недостающие
   проектные зависимости штатным способом с учетом lock-файлов и разрешений.
   Не обходи запреты, не повышай права и не устанавливай системные SDK без
   требуемого разрешения. При блокере сообщи точную причину и необходимое
   действие; не объявляй непроведенную проверку успешной.
3. Используй подходящий установленный runner или создай проектный модуль
   `.focused-spec/runners/<id>.ts` по API `focused-spec/runner` и guidance
   установленного навыка. Зарегистрируй его в `.focused-spec/config.yaml`,
   сохраняя настройки проекта.
   Повторная установка agent-kit или ручной выбор адаптера пользователем не
   нужны. Требования и реализация остаются в пределах разрешенной роли.
4. Для подходящего стека можно взять неактивный пример из
   `.opencode/skills/focused-spec/references/runner-templates/.focused-spec/runners/`:
   `py-unittest` (`<каталог>::<id unittest>`) либо `dotnet-xunit`
   (`<csproj>::<полное имя теста>`, Fact или все случаи одного Theory).
   Копируй только нужный адаптер с его helper-файлами; не активируй остальные.
   Эти примеры не ограничивают выбор фреймворка.
5. Проверь разрешение и реальное выполнение точного теста по workflow навыка.
   Добавь проверки адаптера и команду их запуска под принятый в проекте
   тестовый инструмент. Команда `test:runners` не создается установщиком.

Флаги команд бери из справки локально установленного CLI, не угадывай их.
Для вызовов и инструкций используй один и тот же проектный CLI, как требует
официальный навык. Полный `validate` разрешает `EVIDENCE` через runner'ы и может
запускать сборку или восстановление зависимостей; `--syntax-only` проверяет
только структуру, не существование и не выполнение тестов.

Дополнения ролей хранятся в `.omo/omo.jsonc` (секция `[opencode]`): только
`prompt_append`, без замены встроенных промптов, навыков и разрешений. Это
обязательные инструкции агентам, а не программная блокировка завершения:
выполнение доказывается результатами команд. После изменения этой настройки
или навыка перезапусти OpenCode (и `opencode serve`, если используется).
